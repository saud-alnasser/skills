# Architecture

Two computed facts, one new script, one policy section, and no new state.

## The claim and the working set are different questions

**The claim** is the set of efforts whose directories the branch's own commits
touch, measured against the merge base with the default branch. **The working
set** is the set of efforts the tree touches right now, staged, unstaged, or
untracked. Confinement compares the working set against the claim.

The distinction is load-bearing. Scope computed from the working tree can never
fire a guard, because the first illegal write enlarges the scope that would have
caught it. Measured from commits, the claim is a fact the run cannot edit by
misbehaving.

An empty claim licenses everything, and that is correct rather than a hole: a
fresh branch with no commits is exactly the state `/specify` opens an effort in,
and the first commit fixes the claim for every turn after it.

## Resolution reads content first and the name second

```
base    = origin/HEAD, else init.defaultBranch if it resolves, else main, else master
claim   = efforts touched by  git diff --name-only <base>...HEAD -- <aep>/efforts/
fallback= where the claim is empty, match the branch name against effort
          directories and ticket files present on the tree
working = efforts touched by  git status --porcelain -z
```

Content first because the branch name is not AEP's to read: `specs.md:218`
assigns naming to the repository, and t3 Code assigns it to itself, generating
`t3code/<8 hex>`
(`[[efforts/51-branch-scope/evidence/research/t3-code-worktrees]]`). Content
answers the same question with no cooperation from whoever named the branch.

The name survives as the fallback because it is the only signal a branch with no
commits of its own has, and because a repository that does name branches after
its efforts gets a correct answer one git invocation cheaper.

## Isolation is read from git, never configured

| Fact | Read from |
| --- | --- |
| this checkout is a linked worktree | `git rev-parse --git-dir` differs from `--git-common-dir` |
| the sibling threads and what each holds | `git worktree list --porcelain` |
| a branch cannot be claimed twice inside a clone | git's own refusal, which names the holder |

Enforced inside a clone, advisory across clones, and the run reports which. AEP
creates, names, and removes nothing the runtime owns.

## Alternatives

| | Advantages | Disadvantages | Risks | Maintenance |
| --- | --- | --- | --- | --- |
| **A. `scope.mjs`, content first** (chosen) | works under any branch name; no new state; one file to reason about; leaves the position pin untouched | a new payload file, and one more script an installed tree carries | base detection wrong widens the claim | one script, one policy section |
| **B. a `scope` command on `position.mjs`** | no new payload file; ships on upgrade with nothing to add to the manifest | conflates drift over time with place in the effort space; forces rewriting `verify.mjs:1970`, which pins that exactly `implement` and `install` invoke that script, and the reasoning written beside it | invites the belief that scope is stored in the marker, which `spec.md` explicitly rejects | two questions in one file, diverging |
| **C. match the branch name only** | trivial; no git plumbing beyond the current branch | resolves `t3code/a1b2c3d4` to nothing, so the guard never engages on the runtime this effort was raised for | looks correct in this repository and does nothing in the one that needs it | a naming convention AEP does not own |
| **D. a session registry in the marker** | explicit; a run can say who else is active | per working tree, so it collides between agents sharing a checkout and does not collide between worktrees; a second copy of a fact git already holds | the registry goes stale and is believed | reaping dead sessions, forever |

B is the one worth naming twice, because it is the cheaper-looking option. It
was rejected on the pin: `verify.mjs:1970` asserts the set of skills that invoke
`position.mjs`, with a comment explaining why the set is exactly two. Every
effort-touching skill invoking it would replace that pin and the reason behind
it, and would put the scope answer inside the script whose whole subject is a
marker the spec rules out as the scope holder.

## The folded correction

`src/skills/plan.md` says it "extends the **same** `spec.md`" and writes the
approach "into `spec.md`". `specs.md:443` requires the approach to live in
`plan.md` beside the spec, and `[[templates/plan.template]]` already says so. The
skill contradicts the specification it implements, and this effort carries the
correction because the alternative is a second effort whose entire content is
three sentences.

It is a **requirement of this effort**, not a passing edit: `spec.md` carries it
as requirement 12 so it is reviewed rather than discovered in the diff.

# Interfaces

```
node .aep/scripts/scope.mjs read  [--root <path-to-.aep>] [--json]
node .aep/scripts/scope.mjs check [--root <path-to-.aep>]
```

`read`, scoped:

```
claim      51-branch-scope
working    51-branch-scope
isolation  worktree, enforced, sibling of 3 at <path>
base       origin/main
```

`read`, unscoped:

```
claim      unscoped
working    -
isolation  checkout, advisory
base       origin/main
```

`check`, on a violation:

```
outside the claim 51-branch-scope:
  .aep/efforts/47-post-merge-labels/spec.md
```

| Exit | `read` | `check` |
| --- | --- | --- |
| 0 | the claim is non-empty | nothing outside the claim |
| 1 | unscoped | something outside it, listed |
| 2 | the tree or git could not be read | same |

The vocabulary is `position.mjs`'s and `frontier.mjs`'s on purpose: `read` and
`check` mean what they already mean, exit 1 is the notable condition rather than
an error, and exit 2 is *could not answer*.

**Resolution, stepwise**, so the implementer decides nothing:

1. `base` is the first that resolves: `git rev-parse --abbrev-ref origin/HEAD`,
   `git config init.defaultBranch` where that ref exists, `main`, `master`.
   Where none resolves, `base` is null and step 2 yields an empty claim.
2. `claim` is empty where `base` is null or `HEAD` is `base`; otherwise the
   effort directories appearing in
   `git diff --name-only <base>...HEAD -- <aep>/efforts/`.
3. Where `claim` is empty, match the current branch name, in this order, against
   what the tree holds: an effort directory name; a `<effort>/...` prefix; a
   ticket filename `<id>-<slug>` unique across efforts. A name matching nothing
   leaves the claim empty, which is `unscoped`.
4. `working` is the effort directories appearing in `git status --porcelain -z`,
   `-z` because a path with a space or a non-ASCII character is quoted otherwise
   and would be silently skipped.
5. `isolation` is `worktree` where `--git-dir` differs from `--git-common-dir`,
   otherwise `checkout`; siblings and their branches come from
   `git worktree list --porcelain`.

`check` fails on any member of `working` outside `claim`, and passes everything
when `claim` is empty.

# Technical Approach

The order, and why it is this one:

1. **`scope.mjs`, `payload.mjs`, `manifest.mjs`.** Nothing else depends on the
   prose, and the script is what every later assertion exercises.
2. **`specs.md`.** The law before the surfaces that cite it: `[[rules/authoring]]`
   forbids shipped text from citing what does not resolve where it is read, and
   `verify.mjs` asserts surfaces *against* the specification, so an assertion
   written first would be asserting against text that does not exist yet.
3. **`policies/execution.md`**, which is where a rule about claiming already
   lives and where the confinement rule joins it.
4. **The skills**, one entry line each, plus the folded `plan.md` correction.
5. **The seeds**: both version-control rules and the t3 Code reference.
6. **`verify.mjs`**, each assertion written and then watched to fail against a
   tree with its subject removed, per `[[rules/authoring]]`.
7. **`adapters.mjs`**, then reinstall this repository's own `.aep/` and re-run
   `validate.mjs`.

# Integration

- **`verify.mjs:1970` is untouched by design.** Scope lives in its own script, so
  the pinned set of skills invoking `position.mjs` stays `implement` and
  `install`. A parallel pin is added naming exactly the skills that invoke
  `scope.mjs`, so a ninth skill acquiring one is a failure rather than a drift.
- **`install.mjs` needs no code change.** It copies `PAYLOAD_SCRIPTS`.
- **`index.mjs` needs no change.** Scripts are not artifacts and appear in no
  index table.
- **`release.mjs` and `stamps.json`** gain a baseline entry for the new file at
  release time, through the existing command.
- **`frontier.mjs` is not extended.** It stays a pure function of one effort's
  tickets; the caller supplies the effort, and where the caller had none it now
  has a script that answers.

# Migration

- **Installed repositories** receive `scope.mjs` on upgrade, because payload
  files are replaced verbatim.
- **Existing effort branches migrate themselves.** The claim is computed from
  what the branch changed, so a branch created before this effort resolves
  correctly with no rename and no marker.
- **Existing ticket branches keep their names.** The namespace change is
  forward-only. A branch already called `17-assignment-and-claim` still resolves
  by content, and renaming live branches would break claims the runtime is
  holding.
- **Repository rules are never edited by an upgrade**, so a repository seeded
  before this keeps a version-control rule with the old branch convention.
  `[[skills/update]]` already reconciles rules against law that changed under
  them, and this is one of those changes: it reports the divergence and the human
  decides.

# Testing Strategy

Every criterion in `spec.md` gets a named check. Fixtures come from
`installFixture()` in `verify.mjs`, which already installs into a temporary git
repository, extended once with a helper that commits and branches inside it.

| Criterion | Checked by |
| --- | --- |
| 1 scope printed, exit codes distinct | run `scope.mjs read` in the fixture on a branch with an effort commit, and on the default branch; assert stdout shape and both exit codes |
| 2 `t3code/<hex>` resolves by content, unscoped before its first commit | fixture branch named `t3code/deadbeef`; assert `unscoped` before the commit and the effort after it. This is the pair that proves content resolution rather than name matching |
| 3 unscoped runs are unchanged | assert the shipped `implement.md` states that an empty claim takes any effort |
| 4 a branch touching two efforts resolves to both | fixture commit touching two effort directories; assert both are listed and that `check` still passes |
| 5 writes outside the claim stop, reads do not | `scope.mjs check` with a modified file under another effort; assert exit 1 and the path in stdout. The read half is prose, asserted over `policies/execution.md` |
| 6 named effort outside the claim: clean switches, dirty stops | asserted over the shipped `implement.md` and `policies/execution.md`, which is where the behaviour is defined; the script reports the state the rule turns on |
| 7 isolation reported both ways | create a real worktree in the fixture with `git worktree add`, run `read` inside it, assert `worktree` and the sibling path; run in the main checkout, assert `checkout` and advisory. Remove the worktree in the same test |
| 8 ticket branches unique across efforts | assert the seed and this repository's rule both carry the `<effort>/` namespace, and that neither shows a bare `<ticket-id>-<slug>` as the ticket branch form |
| 9 new effort branch base read from the rule | assert `specify.md` reads `[[rules/version-control]]` for the base and names both shapes |
| 10 scope and isolation appear in `Position` | assert each skill that names an effort invokes `scope.mjs`, and that the set is exactly those skills |
| 11 the suite moves in the same pass | the run itself, plus the deliberate-perturbation discipline below |
| 12 `plan.md` says the approach lives in `plan.md` | assert `skills/plan.md` names `plan.md` as its output and no longer says it extends `spec.md` |

**Each new assertion is watched to fail.** `[[rules/authoring]]` names the
recurring defect: a guard matching something travelling with its subject rather
than the subject. The perturbation for the content-resolution assertions is to
rename the branch, which must *not* change the answer, and to remove the effort
commit, which must.

# Operational Considerations

- **Cost per skill entry is one process and up to five git invocations**, all
  local and none touching the network. `read` runs on entry; `check` runs before
  landing.
- **Nothing is done by hand.** No hook is installed, no configuration is added,
  and no branch is renamed.
- **One thing a person should check in a t3 Code repository:** that the worktree
  path is gitignored. If `.t3-worktrees/` is tracked as untracked content,
  `position.mjs` folds it into the tree fingerprint through
  `git ls-files --others`, and every thread reads as drifted from the moment a
  sibling exists. The seeded reference gains that line.

# Technical Risks

- **Base detection is the single point of failure.** A wrong or stale base
  widens the diff and so widens the claim. It fails **open**: a wider claim
  permits more, so a run is never stopped from doing something legitimate. That
  is the right direction for a guard whose worst outcome would otherwise be
  blocking correct work.
- **Squash merges empty the claim.** After an effort merges, its old branch
  diffs to nothing against the default branch, so the claim empties and the run
  reads unscoped. Correct, and worth stating so it is not filed as a bug.
- **Windows path separators.** `git` prints POSIX separators and `path.join`
  produces backslashes here. Every comparison normalises through the existing
  `toPosix` helper rather than comparing raw strings, which is the bug this
  repository's own suite would otherwise catch late and on one platform only.
- **A worktree test that leaks.** `git worktree add` inside a fixture leaves a
  registration in the common `.git` if the test throws before removing it.
  The fixture directory is temporary, so the leak dies with it, but the test
  removes the worktree explicitly rather than relying on that.

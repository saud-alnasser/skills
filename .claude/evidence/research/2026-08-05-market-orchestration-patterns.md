# How do agent frameworks in the wild structure orchestration, and what makes it additive?

Verified against: `mattpocock/skills` @ `main` (fetched 2026-08-05); Anthropic engineering posts *Building effective agents* and *How we built our multi-agent research system* (fetched 2026-08-05); Claude Code docs `code.claude.com/docs/en/{sub-agents,agent-teams,costs}` (pages self-date to v2.1.178–v2.1.218, fetched 2026-08-05); LangGraph docs `docs.langchain.com/oss/python/langgraph/{graph-api,use-graph-api,use-subgraphs}` (fetched 2026-08-05); CrewAI docs `docs.crewai.com/en/concepts/{crews,tasks,agents,flows}` (fetched 2026-08-05); Microsoft AutoGen `stable` docs (fetched 2026-08-05); `openai/swarm` README @ `main` and OpenAI Agents SDK docs `openai.github.io/openai-agents-python/{multi_agent,tools,results}` (fetched 2026-08-05). As of 2026-08-05.

Status: Open questions listed at the end. Nothing was run, installed, or executed; every claim is read from a project's own repository or documentation site.

## Answer

**The frameworks split cleanly into two families, and the split is exactly the additive/invasive line.**

**Family A — the orchestrator *names* the unit.** The unit keeps its existing shape; orchestration is a call-site wrapper or a name reference. Nothing about the unit changes to fan out five of it. This family: Claude Code subagents (`.claude/agents/*.md`, referenced by name), Claude Code agent teams (reuses those same subagent definitions), `mattpocock/skills` (inline prompt + N `Agent` tool calls, no artifact at all), OpenAI Agents SDK (`Agent.as_tool()`, `@function_tool`), CrewAI **Flows** (`@listen` method calls `SomeCrew().crew().kickoff()` unchanged), AutoGen **AgentChat** (existing `AssistantAgent` passed into a team list; plain functions wrapped by `FunctionTool`).

**Family B — the orchestrator *contains* the unit.** The unit must be re-declared in the orchestration layer's own vocabulary. This family: CrewAI **crews** (work must become `Agent` role/goal/backstory + `Task` description/expected_output), AutoGen **Core** (agents inherit `RoutedAgent`, handlers carry `@message_handler`), and LangGraph in the specific sense that units must be `(state) -> partial-state` callables and the *shared state schema* must gain a reducer for every key two branches write.

**The single most transferable finding for AEP:** the cheapest additive mechanism observed in production docs is **reference by name plus a per-call brief** — Claude Code's subagent definition is one markdown file with `name`/`description` frontmatter, and the exact same definition is spawned as a delegated subagent *or* as an agent-team teammate with no edit ([sub-agents](https://code.claude.com/docs/en/sub-agents), *Choose the subagent scope*; [agent-teams](https://code.claude.com/docs/en/agent-teams), *Use subagent definitions for teammates*). The second most transferable: the *brief*, not the *registry*, is where every framework and Anthropic's own post concentrate the engineering effort.

**The one thing that reliably forces edits to existing artifacts is result merging.** LangGraph is the only framework here that makes conflict handling explicit and mandatory, and it does so by requiring a change to a *central shared* artifact (the state schema's reducers), not to the units. Everyone else either avoids merge entirely (results return as text to a lead who synthesises) or serialises the work so merge never happens.

## Findings

### Where the decomposition is declared

- **mattpocock/skills**: nowhere as a separate artifact — decomposition is prose inside a single `SKILL.md`. `/code-review` instructs: "Send one message with two `Agent` tool calls using the `general-purpose` subagent." — [skills/engineering/code-review/SKILL.md](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/code-review/SKILL.md), *Spawn Parallel Sub-Agents*. The repo has no `.claude/agents/` directory; the 17 engineering skills are all `SKILL.md` + an `agents/openai.yaml` — [repo tree @ main](https://api.github.com/repos/mattpocock/skills/git/trees/main?recursive=1).
- **mattpocock/skills**: the per-skill `agents/openai.yaml` is *not* a decomposition artifact. It is two fields — `interface.display_name` / `interface.short_description`, and `policy.allow_implicit_invocation` — [skills/engineering/ask-matt/agents/openai.yaml](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/ask-matt/agents/openai.yaml). Its purpose is stated as Codex UI metadata plus invocation policy, with the rule "Keep the two in sync: a skill is user-invoked in both harnesses or neither" — [.agents/invocation.md](https://raw.githubusercontent.com/mattpocock/skills/main/.agents/invocation.md).
- **Anthropic's multi-agent research system**: runtime-generated, not declared. "The lead agent ... decomposes queries into subtasks and describes them to subagents" and "spawns subagents to explore different aspects simultaneously" — [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system). No config file is described.
- **Anthropic, *Building effective agents***: names five patterns as building blocks, of which two are decomposition patterns — Parallelization ("Sectioning: Breaking a task into independent subtasks run in parallel" / "Voting") and Orchestrator-workers ("A central LLM dynamically breaks down tasks, delegates them to worker LLMs, and synthesizes their results") — [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents). Decomposition in orchestrator-workers is explicitly *dynamic*, i.e. runtime, not declared.
- **Claude Code subagents**: a per-role markdown file with YAML frontmatter, in `.claude/agents/` (project) or `~/.claude/agents/` (user), scanned recursively; "identity comes only from the `name` frontmatter field" — [sub-agents](https://code.claude.com/docs/en/sub-agents), *Choose the subagent scope*. A definition declares a *role*, never a decomposition; the split into N parts happens at runtime in the parent's Agent tool calls.
- **Claude Code agent teams**: a **shared task list** on disk at `~/.claude/tasks/{team-name}/`, with team config at `~/.claude/teams/{team-name}/config.json`. "Claude Code generates both of these automatically at session startup"; the config "holds runtime state ... so don't edit it by hand or pre-author it: your changes are overwritten on the next state update" — [agent-teams](https://code.claude.com/docs/en/agent-teams), *Architecture*. So the decomposition artifact exists and is durable, but is machine-owned, not authored.
- **LangGraph**: a graph built in code — `builder = StateGraph(State); builder.add_node(step_1); builder.add_edge(START, "step_1"); graph = builder.compile()` — [Use the graph API](https://docs.langchain.com/oss/python/langgraph/use-graph-api). Runtime-variable fan-out is the `Send` API: `return [Send("generate_joke", {"subject": s}) for s in state["subjects"]]` — same page, *Map-reduce*.
- **CrewAI**: a declarative config file. New projects use `crew.jsonc` listing `agents` by name and an inline `tasks` array; classic projects use `config/agents.yaml` + `config/tasks.yaml` with a `@CrewBase` class — [Crews](https://docs.crewai.com/en/concepts/crews). Verbatim example: `{"name": "Market Research Crew", "agents": ["researcher","analyst"], "tasks": [...], "process": "sequential", "verbose": true, "memory": true, "inputs": {"topic": "AI Agents"}}` — same page.
- **CrewAI Flows**: a Python class with `@start()` / `@listen()` / `@router()` decorated methods; "All satisfied `@start()` methods will execute (often in parallel) when the Flow begins or resumes" — [Flows](https://docs.crewai.com/en/concepts/flows).
- **AutoGen AgentChat**: a participant list passed to a team constructor — `RoundRobinGroupChat([primary_agent, critic_agent], termination_condition=text_termination)` — [Teams tutorial](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/teams.html); and `SelectorGroupChat([planning_agent, web_search_agent, data_analyst_agent], model_client=..., ...)` — [SelectorGroupChat](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/selector-group-chat.html).
- **AutoGen Core**: topic-based registration and subscription — `await AIAgent.register(runtime, type=triage_agent_topic_type, factory=lambda: AIAgent(...))` then `await runtime.add_subscription(TypeSubscription(topic_type=..., agent_type=...))` — [Handoffs design pattern](https://microsoft.github.io/autogen/stable/user-guide/core-user-guide/design-patterns/handoffs.html).
- **OpenAI Swarm**: no decomposition artifact. An `Agent` is a dataclass with `name`, `model` (default `gpt-4o`), `instructions`, `functions`, `tool_choice`; routing is a plain function that returns another `Agent` — [swarm README @ main](https://raw.githubusercontent.com/openai/swarm/main/README.md).
- **OpenAI Agents SDK**: two declared modes rather than one artifact — "orchestrating via LLM" (handoffs / agents-as-tools, decided at runtime) and "orchestrating via code" (chaining, loops, parallel execution written by hand) — [Orchestrating multiple agents](https://openai.github.io/openai-agents-python/multi_agent/).

### Brief structure

- **Anthropic (the most explicit published schema)**: "Each subagent needs an objective, an output format, guidance on the tools and sources to use, and clear task boundaries. Without detailed task descriptions, agents duplicate work, leave gaps, or fail to find necessary information." — [multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system). Four required fields; no file format, prose in the spawn call.
- **Anthropic, failure mode when the brief is thin**: "one subagent explored the 2021 automotive chip crisis while 2 others duplicated work investigating current 2025 supply chains, without an effective division of labor" — same source.
- **mattpocock/skills — a real template, quoted verbatim from the Standards sub-agent brief**: *"Report — per file/hunk where relevant — (a) every place the diff violates a documented standard: cite the standard (file + the rule); and (b) any baseline smell you spot: name it and quote the hunk. Distinguish hard violations from judgement calls — documented-standard breaches can be hard, but baseline smells are always judgement calls, and a documented repo standard overrides the baseline. Skip anything tooling enforces. Under 400 words."* — [code-review/SKILL.md](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/code-review/SKILL.md). Note the shape: inputs (diff command, commit list, standards files, smell baseline), output shape (a/b/c enumerated), a precedence rule, an exclusion, and a **length cap**. There is no schema — it is prose, written once per call site.
- **mattpocock/skills — Spec sub-agent brief, verbatim**: *"Report: (a) requirements the spec asked for that are missing or partial; (b) behaviour in the diff that wasn't asked for (scope creep); (c) requirements that look implemented but where the implementation looks wrong. Quote the spec line for each finding. Under 400 words."* — same file.
- **Claude Code subagents — the *role* half of the brief is a schema**: required `name`, `description`; optional `tools`, `disallowedTools`, `model`, `permissionMode`, `maxTurns`, `skills`, `mcpServers`, `hooks`, `memory`, `background`, `effort`, `isolation`, `color`, `initialPrompt` — [sub-agents](https://code.claude.com/docs/en/sub-agents), *Supported frontmatter fields*. The *task* half is freeform prose in the Agent tool call. The body "becomes the system prompt"; "Subagents receive only this system prompt plus basic environment details like the working directory, not the full Claude Code system prompt" — same page.
- **Claude Code agent teams — the brief must be self-contained**: "Teammates load project context automatically, including CLAUDE.md, MCP servers, and skills, but they don't inherit the lead's conversation history. ... Include task-specific details in the spawn prompt." The worked example brief names the target path, the focus areas, a stated system fact ("The app uses JWT tokens stored in httpOnly cookies"), and an output shape ("Report any issues with severity ratings") — [agent-teams](https://code.claude.com/docs/en/agent-teams), *Give teammates enough context*.
- **CrewAI — the most schematised brief of any framework here.** Agent fields: `role`, `goal`, `backstory`, `llm`, `tools`, `allow_delegation`, `max_iter`, `max_rpm`, `verbose`, `cache`, plus `max_execution_time`, `max_retry_limit`, `respect_context_window`, `multimodal`, `reasoning`, `inject_date` — [Agents](https://docs.crewai.com/en/concepts/agents). Task fields: `description`, `expected_output` (both required), `name`, `agent`, `tools`, `context`, `output_file`, `output_json`, `output_pydantic`, `markdown`, `async_execution`, `create_directory`, `guardrail`, `guardrails`, `guardrail_max_retries`, `callback`, `human_input`, `config` — [Tasks](https://docs.crewai.com/en/concepts/tasks). `expected_output` is defined as "A detailed description of what the task's completion looks like" — i.e. CrewAI makes done-criteria a first-class required field.
- **CrewAI YAML task template, verbatim**: `analysis_task:\n  description: >\n    Analyze the market data and create a detailed report\n  expected_output: >\n    A comprehensive analysis with charts and key findings\n  agent: analyst\n  markdown: true\n  output_file: analysis.md` — [Tasks](https://docs.crewai.com/en/concepts/tasks).
- **OpenAI Agents SDK**: the brief is the tool description at the call site — `spanish_agent.as_tool(tool_name="translate_to_spanish", tool_description="Translate the user's message to Spanish")` — [Tools](https://openai.github.io/openai-agents-python/tools/). No schema beyond name + description; the child's own `instructions` carry the rest.
- **AutoGen AgentChat**: `AssistantAgent("agent_name", model_client=..., system_message="Instructions here", tools=[tool_function])` — [Teams tutorial](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/teams.html). No structured brief; the shared conversation is the brief.

### Result integration

- **mattpocock/skills — deliberate non-merge.** Verbatim: *"Present the two reports under `## Standards` and `## Spec` headings, verbatim or lightly cleaned. Do **not** merge or rerank findings — the two axes are deliberately separate. ... Don't pick a single winner across axes — that's the reranking the separation exists to prevent."* — [code-review/SKILL.md](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/code-review/SKILL.md). Conflict between two children is handled by *refusing to resolve it*: both survive, side by side, labelled. This is the only framework surveyed that treats non-merge as the designed outcome.
- **Anthropic**: freeform return to the lead plus a dedicated post-processing agent — subagents "return a list of companies to the lead agent so it can compile a final answer", and a CitationAgent "processes the documents and research report to identify specific locations for citations" — [multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system). Anthropic explicitly recommends *bypassing* the lead for bulk output: "Rather than requiring subagents to communicate everything through the lead agent, implement artifact systems where specialized agents can create outputs that persist independently" — same source. That is the filesystem-as-blackboard pattern, stated as a lesson learned.
- **Claude Code subagents**: text summary to the caller only. "the subagent does that work in its own context and returns only the summary"; a background subagent's "results reach Claude as a completion notification in a later turn" — [sub-agents](https://code.claude.com/docs/en/sub-agents). With nested subagents, "Only the top-level subagent's summary returns to you" — same page.
- **Claude Code subagents — git as the integration surface**: `isolation: worktree` runs a subagent "in a temporary git worktree, giving it an isolated copy of the repository branched by default from your default branch rather than the parent session's `HEAD`. The worktree is automatically cleaned up if the subagent makes no changes" — [sub-agents](https://code.claude.com/docs/en/sub-agents), frontmatter table.
- **Claude Code agent teams**: three surfaces — a shared task list, a per-agent mailbox at `~/.claude/teams/{team-name}/inboxes/{agent-name}.json`, and the working tree. Conflict handling on the task list is real: "Task claiming uses file locking to prevent race conditions when multiple teammates try to claim the same task simultaneously" — [agent-teams](https://code.claude.com/docs/en/agent-teams). Conflict handling on files is *not*: "Two teammates editing the same file leads to overwrites. Break the work so each teammate owns a different set of files" — same page, *Avoid file conflicts*. The documented remedy is partitioning, not merging.
- **LangGraph — the only framework with a formal merge contract.** Parallel branches write into a typed shared state; a key written by more than one branch needs a reducer: `class State(TypedDict): messages: Annotated[list[AnyMessage], add]`, where "The `operator.add` reducer fn makes this append-only" — [Use the graph API](https://docs.langchain.com/oss/python/langgraph/use-graph-api). Conflict is an error, not a silent last-write-wins: "When nodes execute in parallel, only one node can use `Overwrite` on the same state key in a given super-step. If multiple nodes attempt to overwrite the same key in the same super-step, an `InvalidUpdateError` will be raised." — same page.
- **CrewAI**: typed and file-based. `TaskOutput` carries `raw`, `pydantic`, `json_dict`, `agent`, `output_format`, `summary`, `messages` — [Tasks](https://docs.crewai.com/en/concepts/tasks). Downstream consumption is declarative via `context`: in the shipped example, `"context": ["research"]` on the analysis task — [Crews](https://docs.crewai.com/en/concepts/crews). `output_file` writes to a shared path (`"output_file": "output/report.md"`). `guardrail`/`guardrails` validate output "before proceeding", with `guardrail_max_retries`. Cross-child conflict is not addressed because the default `process` is `sequential`.
- **AutoGen AgentChat**: a `TaskResult` with `messages` (all messages from the team) and `stop_reason` — [Teams tutorial](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/teams.html). Integration is by broadcast: a selected speaker's response "is then broadcasted to all other participants", and "the conversation context is kept within the team and all participants" — [SelectorGroupChat](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/selector-group-chat.html). There is no merge because there is no parallelism — participants take turns.
- **OpenAI Agents SDK**: `RunResult` exposes `final_output`, `new_items`, `last_agent`. `final_output` is "An object of type `last_agent.output_type`, if the last agent had an output type defined", else a string — [Results](https://openai.github.io/openai-agents-python/results/). Notably, typing degrades under handoffs: "Handoffs can change which agent finishes the run, so the SDK cannot statically know the full set of possible output types", so `final_output` is typed `Any` — same page. Agents-as-tools sidesteps this: the manager "keeps control of the conversation" and combines outputs itself — [Orchestrating multiple agents](https://openai.github.io/openai-agents-python/multi_agent/).
- **OpenAI Swarm**: a function may return a `Result` object "containing a value, agent reference, and updated context variables simultaneously" — [swarm README](https://raw.githubusercontent.com/openai/swarm/main/README.md). No merge semantics; Swarm is single-threaded handoff.

### Additive vs invasive

*The question answered for each: I already have a working capability. To run five of them in parallel under this framework, what must I change about it?*

- **mattpocock/skills — nothing, and there is nothing to register.** The parent writes N briefs inline and issues N `Agent` tool calls against the built-in `general-purpose` type in one message ([code-review/SKILL.md](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/code-review/SKILL.md), *Spawn Parallel Sub-Agents*). No manifest, no base class, no adapter — because the unit is prose and the runtime already has a generic worker. **Cost of the approach:** the brief is not a reusable artifact. It lives at one call site, and a second skill wanting the same reviewer re-types it. The repo has 17 engineering skills and no `.claude/agents/` directory ([repo tree @ main](https://api.github.com/repos/mattpocock/skills/git/trees/main?recursive=1)) — orchestration here is a *technique documented inside one skill*, not a layer.
- **Claude Code subagents — nothing, by name reference.** A definition is a standalone markdown file added under `.claude/agents/`; adding it changes no existing skill or command. Fan-out is N Agent calls naming the same type. The load-bearing detail for a framework designer: **the identity is the `name` field, and directory layout is irrelevant** — "Claude Code scans `.claude/agents/` and `~/.claude/agents/` recursively, so you can organize definitions into subfolders ... The subdirectory path doesn't affect how a subagent is identified or invoked, because identity comes only from the `name` frontmatter field" — [sub-agents](https://code.claude.com/docs/en/sub-agents). That is what makes it composable: the orchestrator holds a name, not a path or an import.
- **Claude Code subagents → agent teams — the clearest published example of one definition serving two orchestration modes unchanged.** "To define reusable teammate roles, use subagent definitions instead." and "This lets you define a role once, such as a security-reviewer or test-runner, and reuse it both as a delegated subagent and as an agent team teammate." Spawning is by prose: `Spawn a teammate using the security-reviewer agent type to audit the auth module.` The definition composes rather than replaces: "The teammate honors that definition's `tools` allowlist and `model`, and the definition's body is appended to the teammate's system prompt as additional instructions rather than replacing it." — [agent-teams](https://code.claude.com/docs/en/agent-teams), *Use subagent definitions for teammates*.
- **Claude Code subagents → agent teams — the documented cost of that composability.** Two frontmatter fields are silently dropped on the teammate path: "The `skills` and `mcpServers` frontmatter fields in a subagent definition are not applied when that definition runs as a teammate. Teammates load skills and MCP servers from your project and user settings, the same as a regular session." — [agent-teams](https://code.claude.com/docs/en/agent-teams). A second silent divergence exists on the background path: a background subagent keeps every MCP tool but only a fixed built-in list (`Read`, `Grep`, `Glob`, `Bash`, `PowerShell`, `Edit`, `Write`, `NotebookEdit`, `WebFetch`, `WebSearch`, `TodoWrite`, `Skill`, `ToolSearch`, `EnterWorktree`, `ExitWorktree`, `Monitor`, `TaskStop`, `SendMessage`, `Artifact`), "so the same definition can resolve to different tools in the foreground and the background. The removal reports no error" — [sub-agents](https://code.claude.com/docs/en/sub-agents), *Available tools*. **This is the concrete failure mode of name-reference composability: the same artifact means different things in different runtimes, quietly.**
- **CrewAI crews — invasive at the unit level, but no subclassing.** To orchestrate work under a crew, it must be re-expressed as an `Agent` (`role`/`goal`/`backstory`) and a `Task` (`description`/`expected_output`) — [Agents](https://docs.crewai.com/en/concepts/agents), [Tasks](https://docs.crewai.com/en/concepts/tasks). That is a rewrite of the *declaration*, not of the logic. An existing Python capability enters as a tool in the `tools` list (`List[BaseTool]`), so the code is wrapped rather than rewritten. **Cost:** you now maintain the same knowledge in two shapes — the capability, and its role/goal prose.
- **CrewAI Flows — the clearest published "orchestration as a strictly additive layer over an existing orchestration."** A Flow method calls an existing crew with no change to the crew: `result = PoemCrew().crew().kickoff(inputs={"sentence_count": self.state.sentence_count})` then `self.state.poem = result.raw` — [Flows](https://docs.crewai.com/en/concepts/flows). The crew's `kickoff()` "executes unchanged; results are captured and stored in flow state" — same page. The pattern: **the higher layer calls the lower layer's public entrypoint and stores the return value in its own state.** No registration, no interface, no adapter. If AEP wants one structural precedent to copy, this is it.
- **AutoGen AgentChat — nothing for tools, nothing for agents.** Plain functions do not need a base class: `def execute_order(product: str, price: int) -> str: ...` then `execute_order_tool = FunctionTool(execute_order, description="Price should be in USD.")` — "Functions remain standalone; the wrapper provides schema generation and tool metadata without inheritance requirements" — [Handoffs design pattern](https://microsoft.github.io/autogen/stable/user-guide/core-user-guide/design-patterns/handoffs.html). Existing agents are passed into a team constructor unchanged — the SelectorGroupChat docs reuse "the planning agent created earlier" directly in the participants list ([SelectorGroupChat](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/selector-group-chat.html)).
- **AutoGen Core — invasive, and this is the one true base-class case in the survey.** "Agents inherit from `RoutedAgent` and use the `@message_handler` decorator": `class AIAgent(RoutedAgent): @message_handler async def handle_task(self, message: UserTask, ctx: MessageContext) -> None:` — plus registration and subscription calls — [Handoffs design pattern](https://microsoft.github.io/autogen/stable/user-guide/core-user-guide/design-patterns/handoffs.html). **Cost:** the unit gains a superclass, a typed message contract, and a runtime registration step. AutoGen's own answer to this cost is to ship AgentChat as the additive layer above Core — the same project offers both, which is itself evidence that the invasive form was too expensive to be the only option.
- **LangGraph — nearly additive for units, invasive for the shared schema.** A node needs no base class: "Nodes are Python functions (either synchronous or asynchronous)" and "Nodes and Edges are nothing more than functions — they can contain an LLM or just good ol' code"; only `state` is required in the signature, `config` and `runtime` are optional, so an existing function can be added via `add_node` unmodified if its parameter already is the state — [Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api). An existing *compiled graph* composes directly when schemas overlap: `builder.add_node("node_1", subgraph)` — "No wrapper function is needed — the subgraph reads from and writes to the parent's state channels automatically." When schemas differ you write a translating node: `def call_subgraph(state: State): subgraph_output = subgraph.invoke({"bar": state["foo"]}); return {"foo": subgraph_output["bar"]}` — [Use subgraphs](https://docs.langchain.com/oss/python/langgraph/use-subgraphs). The stated composability principle: "as long as the subgraph interface (the input and output schemas) is respected, the parent graph can be built without knowing any details of the subgraph" — same page. **The invasive part is elsewhere:** to fan out five branches you must edit the *shared state definition* to add a reducer for every key more than one branch writes, or the run fails with `InvalidUpdateError` ([Use the graph API](https://docs.langchain.com/oss/python/langgraph/use-graph-api)). That is a change to a central artifact every unit already depends on.
- **OpenAI Agents SDK — nothing; a wrapper at the call site.** An existing agent becomes a callable subunit with one method: `spanish_agent.as_tool(tool_name="translate_to_spanish", tool_description="Translate the user's message to Spanish")`, and an existing function becomes a tool with one decorator — [Tools](https://openai.github.io/openai-agents-python/tools/). The SDK names the choice explicitly: "Use **agents as tools** when a specialist should help with a bounded subtask but should not take over the user-facing conversation. Use **handoffs** when routing itself is part of the workflow." — [Orchestrating multiple agents](https://openai.github.io/openai-agents-python/multi_agent/).
- **OpenAI Swarm — nothing, because there is almost nothing.** Handoff is "a function returns another `Agent` object" and execution transfers; Swarm "runs (almost) entirely on the client and ... does not store state between calls" — [swarm README](https://raw.githubusercontent.com/openai/swarm/main/README.md). **The minimalism is the finding, but so is its fate:** Swarm is "experimental, educational", superseded, with "We recommend migrating to the Agents SDK for all production use cases" — same README. Statelessness plus function-return handoff was insufficient in production; the replacement added typed results, tracing, and guardrails while *keeping* the two additive wrappers (`as_tool`, `@function_tool`).

### Anti-patterns and cost

- **Anthropic, token multiples**: "agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats" — [multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system). Also: "token usage by itself explains 80% of the variance" in the performance benchmark.
- **Anthropic, the economic gate**: "For economic viability, multi-agent systems require tasks where the value of the task is high enough to pay for the increased performance." — same source.
- **Anthropic, when *not* to use it**: avoid where tasks require "all agents to share the same context or involve many dependencies", and note that most coding tasks have "fewer truly parallelizable tasks than research" — same source. This is the closest published statement to a hard exclusion, and it names coding specifically.
- **Anthropic, the upside number for honesty**: parallelism "cut research time by up to 90% for complex queries", and an Opus-lead/Sonnet-subagent system "outperformed single-agent Claude Opus 4 by 90.2%" — same source.
- **Anthropic, debugging**: "Agents make dynamic decisions and are non-deterministic between runs, even with identical prompts. This makes debugging harder." — same source.
- **Anthropic, error compounding**: "Agents can run for long periods of time, maintaining state across many tool calls. This means we need to durably execute code and handle errors along the way. Without effective mitigations, minor system failures can be catastrophic for agents." — same source.
- **Anthropic, *Building effective agents***: "For many applications, however, optimizing single LLM calls with retrieval and in-context examples is usually enough", the guidance being to find "the simplest solution possible, and only increasing complexity when needed"; and "Agentic systems often trade latency and cost for better task performance" with "higher costs, and the potential for compounding errors" — [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents).
- **Claude Code, a published multiple for teams**: "Agent teams use approximately 7x more tokens than standard sessions when teammates run in plan mode, because each teammate maintains its own context window and runs as a separate Claude instance." — [costs](https://code.claude.com/docs/en/costs), *Manage agent team costs*.
- **Claude Code, when not to use a team**: "Agent teams add coordination overhead and use significantly more tokens than a single session. They work best when teammates can operate independently. For sequential tasks, same-file edits, or work with many dependencies, a single session or subagents are more effective." — [agent-teams](https://code.claude.com/docs/en/agent-teams).
- **Claude Code, sizing guidance**: "Start with 3-5 teammates for most workflows"; "Having 5-6 tasks per teammate keeps everyone productive"; "Three focused teammates often outperform five scattered ones"; diminishing returns are explicit — "beyond a certain point, additional teammates don't speed up work proportionally" — same page, *Choose an appropriate team size*.
- **Claude Code, task sizing anti-patterns**: "Too small: coordination overhead exceeds the benefit. Too large: teammates work too long without check-ins, increasing risk of wasted effort." — same page.
- **Claude Code, published failure modes of a real multi-agent implementation** (unusually candid, worth reading in full as a risk list): no session resumption with in-process teammates; "Task status can lag: teammates sometimes fail to mark tasks as completed, which blocks dependent tasks"; "Lead shuts down before work is done"; "Sometimes the lead starts implementing tasks itself instead of waiting for teammates"; "Teammates may stop after encountering errors instead of recovering"; no nested teams; lead is fixed for the session's lifetime — [agent-teams](https://code.claude.com/docs/en/agent-teams), *Limitations* and *Troubleshooting*.
- **Claude Code, a security-relevant boundary worth copying**: "When one agent sends another a message over `SendMessage`, the receiving agent is told it came from another Claude session, not from you. A teammate cannot approve a permission prompt or supply consent on your behalf, and a teammate that was denied an action cannot relay it to another teammate to bypass the check." — same page, *Permissions*.
- **Claude Code, when a subagent is *worth* it** (the positive criterion): "Use one when a side task would flood your main conversation with search results, logs, or file contents you won't reference again"; "Define a custom subagent when you keep spawning the same kind of worker with the same instructions." — [sub-agents](https://code.claude.com/docs/en/sub-agents).
- **AutoGen, the single-agent-first rule**: "start with a single agent for simpler tasks, and transition to a multi-agent team when a single agent proves inadequate" and "Ensure that you have optimized your single agent with the appropriate tools and instructions before moving to a team-based approach." — [Teams tutorial](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/teams.html).
- **OpenAI Agents SDK, the determinism argument**: code-driven orchestration "offers more predictable speed, cost and performance" than letting the LLM direct the flow — [Orchestrating multiple agents](https://openai.github.io/openai-agents-python/multi_agent/).
- **mattpocock/skills, an anti-pattern stated as a positive design rule**: the two review sub-agents run separately "so neither pollutes the other", and merging their findings is explicitly forbidden — [code-review/SKILL.md](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/code-review/SKILL.md). The named risk is that one axis masks the other.

## Limitations

- **The fetch tool summarises.** Every page was retrieved through a fetch tool that converts and condenses HTML before I read it. Quoted strings are reproduced as that tool returned them. Long verbatim passages are reliable in substance; treat exact punctuation and line breaks as approximate, and re-read the source before quoting any of this into a public artifact.
- **Two pages were read in full, unsummarised** — Claude Code's `sub-agents` and `agent-teams` — so those claims are the strongest here. LangGraph, CrewAI, AutoGen, and the OpenAI SDKs were read through per-page summarisation prompts.
- **No version pins for the Python frameworks.** LangGraph, CrewAI, AutoGen, and the Agents SDK were read from their current live documentation on 2026-08-05, not from a tagged release. CrewAI in particular has moved from YAML-first to JSONC-first configuration; older material describing `agents.yaml`/`tasks.yaml` as the default is now the "classic" path.
- **Nothing was executed.** No install, no experiment. Behavioural claims — `InvalidUpdateError`, worktree cleanup, mailbox validation, the 7× teams multiple — are documentation claims, not observations.
- **One category of source is secondary and is flagged inline:** none of the findings above rest solely on a secondary source. A web search on LangGraph's `Send`/reducer semantics surfaced only blogs and DeepWiki; I did not use them — every LangGraph claim here comes from `docs.langchain.com`.
- **Anthropic's two engineering posts are first-party but are published write-ups, not reference specifications.** They describe Anthropic's own systems retrospectively. The four-field subagent brief is a stated lesson, not an enforced schema, and no artifact format backs it.
- **The Claude Code docs describe a fast-moving, partly experimental surface.** Agent teams are "experimental and disabled by default", with behaviour changing across v2.1.178–v2.1.210 within the page itself. Any design built on that specific mechanism inherits that instability.
- **`mattpocock/skills` was read at `main` with no commit pin**, and its orchestration surface is genuinely small — one skill (`/code-review`) spawning two inline sub-agents, plus `/research` described as a background agent. Do not over-read a single example as a framework pattern.

## Open questions

1. **Does `mattpocock/skills` have any convention for a *reusable* sub-agent brief?** The evidence says no — no `.claude/agents/` directory, briefs written inline per call site. Whether that is a deliberate position or simply unexplored is not stated anywhere I read. Worth asking directly if it matters.
2. **What does Claude Code's `Agent` tool actually accept per invocation?** The frontmatter schema is fully documented; the per-call parameter surface (beyond `run_in_background`, `model`, `isolation`, `subagent_type`) is not, and that is the surface an AEP orchestration layer would sit on.
3. **How do the additive frameworks handle a child that fails?** Only Anthropic ("minor system failures can be catastrophic") and Claude Code ("teammates may stop after encountering errors instead of recovering") say anything, and neither offers a mechanism. Retry, partial-result, and compensation semantics are undocumented across the board.
4. **Is there a published framework that versions or contracts the brief?** CrewAI's `expected_output` + `guardrail` is the closest, but nothing surveyed treats the parent→child brief as a checked interface. If AEP wants briefs to be verifiable artifacts, there appears to be no prior art to copy.
5. **Cost of the Claude Code foreground/background tool divergence in practice.** The docs state the same definition resolves to different tools in each mode and that "the removal reports no error". How often that silently breaks a definition is unmeasured and unmeasurable from documentation.
6. **No survey of Claude Code *plugin* frameworks other than AEP's own ancestor.** The brief asked for "any Claude Code skill/plugin framework doing parallel agents with real adoption"; the two with clearly real adoption are Claude Code's own built-ins (subagents, agent teams). Whether a third-party plugin marketplace entry has a distinct orchestration pattern was not established.

# How do Anthropic's first-party orchestration surfaces structure multi-agent work?

Verified against: Claude Code 2.1.222 (`claude --version`), code.claude.com as of 2026-08-05
Status: eight open questions remain — the Workflow tool's input schema, the workflow script API beyond `agent()`/`pipeline()`, `schema` enforcement semantics, worktree isolation inside a workflow, `runId`/`resumeFromRunId`, `budget`, whether hooks fire inside workflow agents, and the agent-team spawn mechanism's parameter surface.

> Companion file: `2026-08-05-claude-code-subagent-orchestration-primitives.md` covers the Agent tool's inheritance, isolation, and limits. Nothing here re-derives that.

## Answer

Anthropic ships **four** first-party orchestration surfaces, and they differ on exactly one axis: **who holds the plan**. The docs state it directly — subagents, skills, agent teams, and workflows "can all run a multi-step task. The difference is who holds the plan" ([Workflows](https://code.claude.com/docs/en/workflows), "When to use a workflow"). Subagents, skills, and agent teams keep the plan in a context window and decide turn by turn; **only dynamic workflows move the decomposition into a durable artifact** — a JavaScript file with `export const meta` and a top-level-`await` body, saved to `.claude/workflows/*.js`. That file is the only place in the whole first-party surface where "this work divides into N parts" is written down as something a machine executes rather than something a model decides.

On the load-bearing question — **additive vs invasive** — every surface is additive, and each names the mechanism. A workflow's `agent()` call takes an `agentType` naming an existing subagent definition; an agent team teammate can be spawned with an existing subagent type, where "the definition's body is appended to the teammate's system prompt as additional instructions rather than replacing it" ([Agent teams](https://code.claude.com/docs/en/agent-teams), "Use subagent definitions for teammates"); a skill becomes a subagent task by adding three frontmatter keys and changing nothing in its body. The shipped `code-modernization` plugin is the proof at scale: six workflow scripts fan out over seven ordinary agent definitions (`legacy-analyst`, `scaffolder`, `uplift-migrator`, …) whose frontmatter carries only `name`, `description`, `tools` — no orchestration awareness whatsoever. Those same commands each carry a **`Fallback` (no Workflow tool)** branch that runs the identical agents in-session, which is the strongest available evidence that fan-out is a wrapper, not a rewrite.

The one place a structured return contract exists is inside a workflow: `agent()` accepts a `schema` option holding a JSON Schema, and the plugin scripts use it to force typed returns (`{sloc: number, built: boolean, playbookGaps: string[]}`). **This is the only structured-output mechanism on any first-party surface.** Everywhere else the return channel is what the prior research found: a text string. Result integration therefore has four distinct modes — script variables (workflows), a shared task list plus mailbox JSON files (teams), a git branch and a draft PR (background sessions and `/batch`), and a text summary (plain subagents). Only workflows and `/batch` have a documented conflict story: workflows via per-agent isolated copies, `/batch` and agent view via one worktree per unit. **Agent teams have none** — "Agent teams don't isolate teammates in worktrees, so partition the work so each teammate owns a different set of files" ([Run agents in parallel](https://code.claude.com/docs/en/agents), "Choose an approach").

## Findings

### Where the decomposition is declared

- **Workflows — a JavaScript file, and it is the only executable decomposition artifact.** "A dynamic workflow is a JavaScript script that orchestrates subagents at scale. Claude writes the script for the task you describe, and a runtime executes it in the background while your session stays responsive." — [Workflows](https://code.claude.com/docs/en/workflows), intro
- The file's format: "the file in `.claude/workflows/` holds a `meta` block followed by a script body that orchestrates subagents… The body is plain JavaScript with top-level `await`. `agent()` spawns one subagent and `pipeline()` runs one per item in a list." — [Workflows](https://code.claude.com/docs/en/workflows), "What the saved script looks like"
- The documented `meta` block in the docs' own example carries only `name` and `description`. — [Workflows](https://code.claude.com/docs/en/workflows), "What the saved script looks like"
- Shape evidence extends `meta`: every shipped official workflow script carries `name`, `description`, **`whenToUse`**, and **`phases: [{title, detail}]`**. Example: `phases: [{ title: 'Find', detail: 'one finder per vulnerability class' }, { title: 'Verify', detail: 'one refuter per finding; second judge for Critical/High' }]` — `C:\Users\saud-alnasser\.claude\plugins\marketplaces\claude-plugins-official\plugins\code-modernization\workflows\harden-scan.js`. `whenToUse` and `phases` are **not documented** on the workflows page; see Open questions.
- Save locations, and the resulting artifact identity: `.claude/workflows/` (project, shared via the repo) or `~/.claude/workflows/` (personal). "The workflow runs as `/<name>` in future sessions from either location." Project wins on a name collision. — [Workflows](https://code.claude.com/docs/en/workflows), "Save the workflow for reuse"
- Plugin distribution: "Place the script in a `workflows/` directory at the plugin root… A plugin called `acme-tools` containing a script whose `meta.name` is `release-audit` runs as `/acme-tools:release-audit`." — [Workflows](https://code.claude.com/docs/en/workflows), "Distribute a workflow in a plugin"
- Two official plugins ship such a directory: `claude-security/workflows/scan.js` (one minified script, 6 phases) and `code-modernization/workflows/` (six scripts, 1,463 lines total) — `C:\Users\saud-alnasser\.claude\plugins\marketplaces\claude-plugins-official\plugins\`
- **Agent teams — nothing declarative. The decomposition is a runtime task list.** "the lead breaks work into tasks and assigns them to teammates automatically". Team state lives at `~/.claude/teams/{team-name}/config.json` and the task list at `~/.claude/tasks/{team-name}/`, but the config "holds runtime state such as session IDs and tmux pane IDs, so don't edit it by hand or pre-author it: your changes are overwritten on the next state update." — [Agent teams](https://code.claude.com/docs/en/agent-teams), "Size tasks appropriately" and "Architecture"
- Explicitly, there is no project-scoped team file: "There is no project-level equivalent of the team config. A file like `.claude/teams/teams.json` in your project directory is not recognized as configuration; Claude treats it as an ordinary file." — [Agent teams](https://code.claude.com/docs/en/agent-teams), "Architecture"
- The team name is not chosen either: "The name is `session-` followed by the first eight characters of the session ID". `TeamCreate`/`TeamDelete` "no longer exist"; the `team_name` input on the Agent tool "is accepted but ignored". — [Agent teams](https://code.claude.com/docs/en/agent-teams), "Architecture" and the v2.1.178 Note
- **Agent view / background sessions — nothing at all. The unit of decomposition is one dispatched prompt, typed by the human.** Dispatch routes are `claude agents` + a typed prompt, `/bg <prompt>` inside a session, or `claude --bg "<prompt>"` from the shell. — [Agent view](https://code.claude.com/docs/en/agent-view), "Dispatching work to background sessions"
- **Skills with `context: fork` — the SKILL.md body *is* the brief; there is no N-way split.** "Add `context: fork` to your frontmatter when you want a skill to run in isolation. The skill content becomes the prompt that drives the subagent." — [Skills](https://code.claude.com/docs/en/skills), "Run skills in a subagent". This is a 1:1 hand-off, not a decomposition.
- **`/batch` — decomposition happens at runtime, gated by human approval, and is never persisted.** `/batch` "Researches the codebase; Decomposes the work into 5 to 30 independent units; Presents a plan for approval; Once approved, spawns one background subagent per unit in an isolated git worktree". — [Commands](https://code.claude.com/docs/en/commands), `/batch`. The docs classify it as "a packaged use of subagents and worktrees, not a separate coordination style." — [Run agents in parallel](https://code.claude.com/docs/en/agents)
- The canonical summary row: "Where intermediate results live — Subagents: Claude's context window / Skills: Claude's context window / Agent teams: A shared task list / Workflows: Script variables". And "What's repeatable — the worker definition / the instructions / the team definition / **the orchestration itself**". — [Workflows](https://code.claude.com/docs/en/workflows), "When to use a workflow"

### Brief structure

- **No prose template for a brief exists on any surface.** No page publishes required sections, a schema, or a checklist for what a parent must tell a child. The nearest thing to guidance is a worked example: "Spawn a security reviewer teammate with the prompt: \"Review the authentication module at src/auth/ for security vulnerabilities. Focus on token handling, session management, and input validation. The app uses JWT tokens stored in httpOnly cookies. Report any issues with severity ratings.\"" — [Agent teams](https://code.claude.com/docs/en/agent-teams), "Give teammates enough context". **This is the only documented brief exemplar in the entire surface.**
- **Workflows DO change the structured-output answer.** The docs' own example passes a JSON Schema to `agent()`:
  ```javascript
  const found = await agent('List every .ts file under src/routes/.', {
    schema: { type: 'object', required: ['files'], properties: { files: { type: 'array', items: { type: 'string' } } } },
  })
  ```
  and the next line dereferences `found.files` as a typed value. — [Workflows](https://code.claude.com/docs/en/workflows), "What the saved script looks like". The prior research's finding — no structured-output mechanism on the plain Agent tool — stands; `schema` inside a workflow is the exception.
- Shape evidence, consistent across every shipped script: the option bag passed to `agent()` uses exactly four keys — `agentType`, `label`, `phase`, `schema` — plus `model` and `effort` in `claude-security/workflows/scan.js`. Counted across all seven official scripts: `label:` 24×, `schema:` 18×, `phase:` 18×, `agentType:` 18×, `effort:` 6×, `model:` 4×. No script uses `tools`, `isolation`, `maxTurns`, `background`, `permissionMode`, `timeout`, `retries`, or `concurrency`.
- Shape evidence for how a real brief is composed: the schema is where the contract lives, and field `description` strings carry the discipline. From `uplift-migrate.js`: `built: { type: 'boolean', description: 'true ONLY if buildRan is true AND the build you ran succeeded — never inferred or assumed. If buildRan is false, built MUST be false.' }`. The script then clamps it in code rather than trusting the agent: `.then(r => (r ? { ...r, built: !!(r.built && r.buildRan), … } : null))` — `code-modernization\workflows\uplift-migrate.js`
- Shape evidence for prompt hygiene at the boundary: every official script fences agent-authored prose before interpolating it into another agent's prompt — `const fence = s => \`<<<UNTRUSTED\n${String(s ?? '').replace(/<<<UNTRUSTED|UNTRUSTED>>>/g, '[fence marker stripped]')}\nUNTRUSTED>>>\`` — and validates every path-shaped `args` value against a regex before it reaches a prompt. — `code-modernization\workflows\reimagine-scaffold.js`, `portfolio-assess.js`, `uplift-migrate.js`
- **Workflow input at invocation time is structured.** "A saved workflow can accept input through the `args` parameter. The script reads it as a global named `args`… Claude passes the list as structured data, so the script can call array and object methods on `args` directly without parsing it first. If `args` is omitted, the global is `undefined` inside the script." — [Workflows](https://code.claude.com/docs/en/workflows), "Pass input to a saved workflow"
- Shape evidence qualifies that: every official script defensively re-parses, with the comment "`args` may arrive as the caller's raw JSON string rather than the parsed object, depending on the invoking runtime" — `code-modernization\workflows\portfolio-assess.js` line 10. The docs and the shipped code disagree; treat `args` as possibly-a-string.
- **The Workflow tool's own call shape is not published.** The tools reference gives it one table row and no behavior section: "`Workflow` — Runs a dynamic workflow: a script that orchestrates many subagents in the background and returns one consolidated result. Permission required: Yes" — [Tools reference](https://code.claude.com/docs/en/tools-reference), tool table. Shape evidence supplies two forms actually used by shipped plugins: `Workflow({ scriptPath: "${CLAUDE_PLUGIN_ROOT}/workflows/portfolio-assess.js", args: {…} })` (`code-modernization/commands/modernize-assess.md`) and `Workflow({ name: "claude-security:scan", args: {…} })` (`claude-security/skills/claude-security/jobs/scan-codebase.md`). Neither `scriptPath` nor `name` is documented.
- **Agent teams — the brief is the spawn prompt, plus the project's own context.** "When spawned, a teammate loads the same project context as a regular session: CLAUDE.md, MCP servers, and skills. It also receives the spawn prompt from the lead. The lead's conversation history does not carry over." — [Agent teams](https://code.claude.com/docs/en/agent-teams), "Context and communication". No structured-output mechanism is documented for a teammate's return.
- One team-only brief modifier: plan-gating. "The teammate works in read-only plan mode until the lead approves their approach… If rejected, the teammate stays in plan mode, revises based on the feedback, and resubmits." The lead decides autonomously; you shape it by putting criteria in your own prompt. — [Agent teams](https://code.claude.com/docs/en/agent-teams), "Require plan approval for teammates"
- **Skills with `context: fork` — the frontmatter is the whole contract.** `context`: "Set to `fork` to run in a forked subagent context." `agent`: "Which subagent type to use when `context: fork` is set." `background`: "Only applies with `context: fork`. Set to `false` to wait for the forked subagent's result in the turn that invoked the skill… Default: `true`. Requires Claude Code v2.1.218 or later." — [Skills](https://code.claude.com/docs/en/skills), frontmatter reference
- The two directions are tabulated: "Skill with `context: fork` — System prompt: From agent type / Task: SKILL.md content / Also loads: CLAUDE.md, except when the agent is Explore or Plan" versus "Subagent with `skills` field — System prompt: Subagent's markdown body / Task: Claude's delegation message / Also loads: Preloaded skills + CLAUDE.md". — [Skills](https://code.claude.com/docs/en/skills), "Run skills in a subagent"
- The one documented failure mode of a fork brief: "`context: fork` only makes sense for skills with explicit instructions. If your skill contains guidelines like \"use these API conventions\" without a task, the subagent receives the guidelines but no actionable prompt, and returns without meaningful output." — [Skills](https://code.claude.com/docs/en/skills), "Run skills in a subagent" (Warning)
- **Hooks can inject into a brief, at exactly one point.** `SubagentStart` "fires for context only. No blocking or decision control is supported. You can use `hookSpecificOutput.additionalContext` to inject context that the subagent sees at startup." Its payload carries `session_id`, `hook_event_name`, `agent_type`, `agent_id`, `cwd`, `permission_mode`. — [Hooks](https://code.claude.com/docs/en/hooks.md), "SubagentStart"
- The injection is one-way and blind: `SubagentStart` **cannot read the delegation prompt** — no prompt field appears in its payload. And a hook error there is invisible to the parent: "Exit code 2 stderr renders in the transcript as a `<hook name> hook error` notice… Claude doesn't see it, and the subagent proceeds. The notice appears in the subagent's own transcript, not in the parent conversation." — [Hooks](https://code.claude.com/docs/en/hooks.md), "SubagentStart"
- Also global, from the prior research and unchanged here: `--append-subagent-system-prompt` appends to every subagent's system prompt including nested ones. — [Create custom subagents](https://code.claude.com/docs/en/sub-agents), "Write subagent files"

### Result integration

- **Workflows — into script variables, then one consolidated value into the conversation.** "The workflow runtime executes the script in an isolated environment, separate from your conversation. Intermediate results stay in script variables instead of landing in Claude's context." — [Workflows](https://code.claude.com/docs/en/workflows), "How a workflow runs". Corroborated by the tools reference: the tool "returns one consolidated result".
- The script's `return` value is what surfaces. Shape evidence: `portfolio-assess.js` ends `return { parentDir, rows: surveyed, unmeasured: failed, complexityIndexFormula: '…' }`; `uplift-migrate.js` returns per-unit results plus three re-passable unit lists.
- **Merging is ordinary JavaScript, and the official scripts do it in code rather than in an agent.** `portfolio-assess.js` computes COCOMO-II uniformly after the fan-out — "COCOMO computed deterministically… computed here so every row uses the identical formula" — and `harden-scan.js` computes a `falsePositiveRate` from the verified set. `code-modernization\workflows\portfolio-assess.js`, `harden-scan.js`
- **Failure is a `null`, and the caller must handle it.** "An `agent()` call resolves to `null` if you stop it mid-run or it hits an unrecoverable API error. `pipeline()` keeps that `null` in the results array, which is why the example ends with `.filter(Boolean)` to drop those entries." — [Workflows](https://code.claude.com/docs/en/workflows), "What the saved script looks like". Every official script does `.filter(Boolean)` and then reconstructs the missing set by difference, e.g. `const failed = systems.filter(s => !surveyed.some(r => r.system === s))`.
- **Conflict handling inside a workflow is by disjoint write scope, asserted in the script and instructed in the prompt.** `uplift-migrate.js` rejects overlapping unit paths before spending any agent — "Unit paths overlap: … parallel agents need disjoint directories" — normalizes case ("these stacks commonly live on case-insensitive filesystems") and rejects segments ending in `.` or space because "on some filesystems (NTFS most of all) \"Lib.\" and \"Lib \" resolve to the same directory". The prompt then states: "WRITE SCOPE (hard rule): edit ONLY inside `${workDir}/${u.path}/`… Two agents racing on a shared file corrupt it for everyone." — `code-modernization\workflows\uplift-migrate.js`
- **Shared-file edits are explicitly excluded from the fan-out and returned upward for the parent to apply.** The schema field: `sharedFileNeeds: 'shared/root-level files this unit needs changed that you did NOT touch — path + the change needed. Owned by the calling session.'`, and the calling command instructs: "**Cross-cutting edits are yours.** Apply the returned `sharedFileNeeds`… yourself — the agents correctly refused to touch files they would race each other on." — `code-modernization\workflows\uplift-migrate.js`, `code-modernization\commands\modernize-uplift.md`
- **Agent teams — a shared task list plus a mailbox, and the lead synthesizes.** "Each agent's mailbox is a JSON file at `~/.claude/teams/{team-name}/inboxes/{agent-name}.json`. Claude Code validates every entry when it reads a mailbox file. Entries that don't match the message format are reported as errors and removed from the file; the valid messages are still delivered." — [Agent teams](https://code.claude.com/docs/en/agent-teams), "Architecture"
- Task dependencies unblock automatically: "when a teammate completes a task that other tasks depend on, it unblocks the dependent tasks without any action from you." Claiming is race-safe: "Task claiming uses file locking to prevent race conditions". — [Agent teams](https://code.claude.com/docs/en/agent-teams), "Architecture" and "Assign and claim tasks"
- **Agent teams have no file-conflict mechanism.** "Two teammates editing the same file leads to overwrites. Break the work so each teammate owns a different set of files." — [Agent teams](https://code.claude.com/docs/en/agent-teams), "Avoid file conflicts". Restated as a decision criterion: "Agent teams don't isolate teammates in worktrees, so partition the work so each teammate owns a different set of files." — [Run agents in parallel](https://code.claude.com/docs/en/agents), "Choose an approach"
- **Background sessions — the integration unit is a git branch and, optionally, a pull request.** "Background sessions use git worktree isolation by default… Before editing files, Claude moves the session into isolated worktree under `.claude/worktrees/`. This allows parallel sessions to read same checkout but each writes to its own branch". When a session finishes with changes, Claude "Commits without asking; Pushes the branch when repository has remote; **Never force-pushes, merges to main/master, or pushes to main/master**", and "opens draft PR when task calls for it". — [Agent view](https://code.claude.com/docs/en/agent-view), "File edits and isolation" / "Handling file changes"
- Isolation is skippable and disableable: skipped when already inside a linked worktree, when the cwd is not a git repo with no `WorktreeCreate` hook, or when the write is outside the working directory; turned off with `{"worktree": {"bgIsolation": "none"}}`. — [Agent view](https://code.claude.com/docs/en/agent-view), "File edits and isolation"
- **`/batch` integrates by pull request, one per unit.** "Each subagent implements its unit, runs tests, and opens a pull request." — [Commands](https://code.claude.com/docs/en/commands), `/batch`
- **`SubagentStop` is the only hook that can act on a result, and it cannot rewrite it.** Its payload carries `last_assistant_message` — "The final text the subagent produced". It "supports blocking and context injection. Use top-level `decision: \"block\"` with a `reason` to prevent the subagent from stopping… Return `hookSpecificOutput.additionalContext` to inject feedback that the parent conversation sees after the subagent completes". — [Hooks](https://code.claude.com/docs/en/hooks.md), "SubagentStop". Nothing lets it modify the returned text.
- `TaskCompleted` gates the *task list*, not a result: payload is `session_id`, `hook_event_name`, `task_id`, `task_title`, `cwd`, `permission_mode` — no result field. It "supports blocking via exit code 2 or `continue: false`". Notably its documented block example uses `{"decision": "block", "reason": …}` while the prose says exit code 2 or `continue: false`; the page is internally inconsistent here. — [Hooks](https://code.claude.com/docs/en/hooks.md), "TaskCompleted"
- `TaskCreated` gates decomposition itself: it "Fires when a task is being created via `TaskCreate`", carrying `task_id`, `task_title`, `task_description`, and can block with exit code 2 or `continue: false`. This is the one hook that can veto a proposed unit of work before it exists. — [Hooks](https://code.claude.com/docs/en/hooks.md), "TaskCreated"
- `TeammateIdle` closes the loop on a teammate declaring itself done: "runs when a teammate is about to go idle. Exit with code 2 to send feedback and keep the teammate working." — [Agent teams](https://code.claude.com/docs/en/agent-teams), "Enforce quality gates with hooks"

### Additive vs invasive

**Every surface is additive. Each names the mechanism.**

- **Workflows: `agentType` points at an existing definition.** The docs never say this outright, but shape evidence is unambiguous: `agent(prompt, { agentType: 'code-modernization:legacy-analyst', … })` in `portfolio-assess.js` targets `code-modernization/agents/legacy-analyst.md`, whose entire frontmatter is `name`, `description`, `tools: Read, Glob, Grep, Bash` — no workflow-specific field, no orchestration awareness. Same for `scaffolder` and `uplift-migrator`. — `C:\Users\saud-alnasser\.claude\plugins\marketplaces\claude-plugins-official\plugins\code-modernization\`
- **The strongest single piece of evidence: the same agents run both ways.** Every `code-modernization` command that uses a workflow carries an explicit non-workflow branch. `modernize-assess.md`: "**Preferred — Workflow orchestration.** If the **Workflow tool** is available…" then "**Fallback** (no Workflow tool): run Steps P1–P3 per system yourself, then P4." `modernize-harden.md`: "**Fallback — direct subagent** (older Claude Code builds without the Workflow tool). Spawn the **security-auditor** subagent". `modernize-extract-rules.md`: "## Method B — Direct subagent fan-out (fallback)". `modernize-uplift.md` likewise. Orchestration is a wrapper that can be removed without touching the capability. — `code-modernization\commands\*.md`
- **Workflows are also additive in the other direction: they cannot reach into the repository at all.** "No direct filesystem or shell access from the workflow itself — Agents read, write, and run commands. The script coordinates the agents." — [Workflows](https://code.claude.com/docs/en/workflows), "Behavior and limits". The shipped scripts state the consequence: "enumerate the immediate subdirectories first — the workflow script has no filesystem access". The script is pure coordination; the capability is untouched.
- **Agent teams: an existing subagent definition becomes a teammate by name, and is appended rather than replaced.** "When spawning a teammate, you can reference a subagent type from any subagent scope: project, user, plugin, or CLI-defined. This lets you define a role once, such as a security-reviewer or test-runner, and reuse it both as a delegated subagent and as an agent team teammate… The teammate honors that definition's `tools` allowlist and `model`, and **the definition's body is appended to the teammate's system prompt as additional instructions rather than replacing it**." — [Agent teams](https://code.claude.com/docs/en/agent-teams), "Use subagent definitions for teammates"
- The additive path has a documented cost: "The `skills` and `mcpServers` frontmatter fields in a subagent definition are not applied when that definition runs as a teammate. Teammates load skills and MCP servers from your project and user settings, the same as a regular session." — [Agent teams](https://code.claude.com/docs/en/agent-teams), same section. A definition that relies on preloaded `skills` silently loses them as a teammate.
- Team coordination tools are injected, not declared: "Team coordination tools such as `SendMessage` and the task management tools are always available to a teammate even when `tools` restricts other tools." — [Agent teams](https://code.claude.com/docs/en/agent-teams), same section. The definition needs no knowledge that a team exists.
- **Skills: three frontmatter keys, zero body changes.** `context: fork`, `agent:`, `background:` are all optional and none touches the body. The docs' own example is a four-line frontmatter block over an unmodified task body. — [Skills](https://code.claude.com/docs/en/skills), "Example: Research skill using Explore agent"
- The tradeoff is documented and real: "A backgrounded fork also runs with the narrower tool set that applies to background subagents… If your skill's steps depend on a tool outside that set, set `background: false` to keep the full tool set." So the wrapper *can* change what the capability can do — but the fix is one frontmatter key, not a rewrite. — [Skills](https://code.claude.com/docs/en/skills), "Run skills in a subagent"
- **Background sessions: a subagent definition dispatches unchanged.** `claude --agent code-reviewer --bg "address review comments on PR 1234"`, and in agent view `<agent-name> <prompt>` or `@<agent-name>` selects a custom subagent. — [Agent view](https://code.claude.com/docs/en/agent-view), "Dispatching work to background sessions"
- **Hooks are the purest additive layer: they attach by matcher, and the agent never knows.** `SubagentStart`/`SubagentStop` match on `agent_type`, "for example, `\"Explore\"` or `\"security-reviewer\"`… For subagents shipped by a plugin, this is the plugin-scoped identifier such as `my-plugin:reviewer`". Nothing is declared in the agent file. — [Hooks](https://code.claude.com/docs/en/hooks.md), "SubagentStart"
- **The one invasive-ish edge:** a workflow script is *written by Claude for the task*, not assembled from parts you own. "Claude writes the script for the task you describe". The reusable artifact is the script, not a composition of scripts — the docs describe no import, include, or sub-workflow mechanism. A workflow that fans out over existing agents is additive with respect to the *agents*, and net-new with respect to the *orchestration*.
- The docs do offer a migration path for an existing hand-rolled orchestrator: "If you already have an orchestrator built another way, such as a folder of subagent prompts or a skill that fans work out, you can point Claude at it and ask for a workflow that does the same thing." — [Workflows](https://code.claude.com/docs/en/workflows), "Ask for a workflow in your prompt"

### Efficiency patterns

**Concurrency and hard caps**

- Workflow runtime: "Up to 16 concurrent agents, fewer on machines with limited CPU cores — Bounds local resource use" and "1,000 agents total per run — Prevents runaway loops". — [Workflows](https://code.claude.com/docs/en/workflows), "Behavior and limits"
- Shape evidence treats the cap as the sizing input: "no cap; the runtime queues agents against its concurrency limit" (`reimagine-scaffold.js` meta), and `uplift-migrate.js` sets `const MAX_BATCH = 16` with the comment "Beyond the runtime's own concurrency cap a bigger batch buys no speed and only coarsens the circuit breaker."
- Agent teams: **no hard limit, only advice.** "There's no hard limit on the number of teammates… Start with 3-5 teammates for most workflows… Having 5-6 tasks per teammate keeps everyone productive." — [Agent teams](https://code.claude.com/docs/en/agent-teams), "Choose an appropriate team size"

**Pipeline vs barrier semantics**

- The docs name exactly two script primitives: "`agent()` spawns one subagent and `pipeline()` runs one per item in a list." No barrier, race, or all-settled primitive is documented. — [Workflows](https://code.claude.com/docs/en/workflows), "What the saved script looks like"
- Shape evidence adds a third, undocumented one: **`parallel()`**, which takes an array of thunks — `await parallel(services.map(svc => () => agent(…)))` — and is used 14× across the official scripts versus `pipeline()` 3×. `pipeline()` is called as `pipeline(items, (item, _orig, i) => …)`. `log()` is used 53× for progress lines. **None of `parallel`, `log`, or the `pipeline` callback's arity is documented.** — `code-modernization\workflows\*.js`, `claude-security\workflows\scan.js`
- The barrier is implicit in `await`. Shape evidence shows the pattern for a real barrier: `uplift-migrate.js` runs `await parallel(batch.map(…))`, then recomputes eligibility from results before forming the next batch — "A unit is only batched once every listed dep has BUILT, so a unit and the unit it depends on never build concurrently in the same working copy."
- Shape evidence for a documented-in-code circuit breaker: "Circuit breaker trips on a batch whose build rate falls below 2/3", with escalating batch sizes `batchNum === 1 ? 1 : batchNum === 2 ? 2 : 4` times a base of 4, capped at 16. The plugin's guidance: "The correct response to a failing batch is a better playbook, not more agents." — `code-modernization\workflows\uplift-migrate.js`, `commands\modernize-uplift.md`
- Shape evidence for a convergence loop: `extract-rules.js` runs `while (dryRounds < 2 && round < maxRounds)` — rounds until two consecutive rounds find nothing new. The docs endorse this shape in prose: "use a workflow to find flaky tests in this repo… stop once two rounds in a row find nothing new". — `extract-rules.js`; [Workflows](https://code.claude.com/docs/en/workflows), "Example workflow prompts"

**Resume / journal**

- "The runtime tracks each agent's result as the run progresses, which is what makes a run resumable within the same session." — [Workflows](https://code.claude.com/docs/en/workflows), "How a workflow runs"
- The replay rules are precise and consequential: "An agent that was still running when you stopped isn't saved, so it starts over on resume. Replay follows the order agents started. Cached results stop at the first agent that didn't finish, and every agent that started after that one runs again, even if it completed." — [Workflows](https://code.claude.com/docs/en/workflows), "Resume after a pause"
- The design conclusion the docs draw from that: "**A workflow that fans work out across many small agents therefore preserves more progress than one long agent.**" — same section. This is the only place in the first-party docs where a granularity decision is argued from a mechanism.
- Resume is session-scoped: "Resume works within the same Claude Code session. If you exit Claude Code while a workflow is running, the next session starts the workflow fresh." — same section
- Every run's script is journaled to disk: "Every run writes its script to a file under your session's directory in `~/.claude/projects/`. Claude receives the path when the run starts, so you can ask for it. You can open that file to read the orchestration Claude wrote, diff it against a previous run's script, or edit it and ask Claude to relaunch from the edited version." — [Workflows](https://code.claude.com/docs/en/workflows), "How a workflow runs"
- Agent teams: **resume is broken.** "No session resumption with in-process teammates: `/resume` and `/rewind` do not restore in-process teammates. After resuming a session, the lead may attempt to message teammates that no longer exist." — [Agent teams](https://code.claude.com/docs/en/agent-teams), "Limitations"

**Cost and token accounting**

- Workflows: "A workflow spawns many agents, so a single run can use meaningfully more tokens than working through the same task in conversation." The mitigation is a dry slice: "run the workflow on a small slice first: one directory instead of the whole repo, or a narrow question instead of a broad one." — [Workflows](https://code.claude.com/docs/en/workflows), "Cost"
- An automatic large-run alarm exists: "When a workflow schedules more than 25 agents, or its projected token total passes 1.5 million, its progress line… shows a `Large workflow` warning… The warning is advisory: it doesn't pause or limit the run." — [Workflows](https://code.claude.com/docs/en/workflows), "Cost"
- A size guideline is sent to Claude as *advice*, not a cap: `unrestricted` / `small` (<5 agents) / `medium` (<15) / `large` (<50), default `medium`, set via `/config workflowSizeGuideline=small` or the `workflowSizeGuideline` settings key. "Claude Code sends the guideline to Claude as advice, not a cap, so a prompt that calls for a different scale still overrides it." — [Workflows](https://code.claude.com/docs/en/workflows), "Set a size guideline"
- Per-stage model routing is the named cost lever: "Every agent in a workflow uses your session's model unless the script routes a stage to a different one or the `CLAUDE_CODE_SUBAGENT_MODEL` environment variable is set, which overrides both." — [Workflows](https://code.claude.com/docs/en/workflows), "Cost". Shape evidence confirms scripts do route: `claude-security/workflows/scan.js` passes `model:` on 4 agent calls and `effort:` on 6.
- Shape evidence for an **undocumented in-script token budget**: `extract-rules.js` reads `if (budget.total && budget.remaining() < 60000) { log('Stopping extraction: token budget nearly exhausted…'); break }`. A `budget` global with `.total` and `.remaining()` appears nowhere in the documentation. — `code-modernization\workflows\extract-rules.js` lines 193–195
- Agent teams carry a published multiplier: "Agent teams use approximately **7x more tokens** than standard sessions when teammates run in plan mode, because each teammate maintains its own context window and runs as a separate Claude instance." — [Manage costs](https://code.claude.com/docs/en/costs), "Manage agent team costs"
- Team cost levers, in order given: "Use Sonnet for teammates… Keep teams small… Keep spawn prompts focused… Shut down teammates when their work is done. Each active teammate continues consuming tokens until it exits or the session ends." — [Manage costs](https://code.claude.com/docs/en/costs), "Agent team token costs"
- Background sessions: "Each session consumes quota independently (10 sessions ≈ 10× quota usage)." — [Agent view](https://code.claude.com/docs/en/agent-view), "Limitations"
- **No caching mechanism is documented for any orchestration surface.** Prompt caching is discussed only for the main conversation. The one caching-adjacent statement is workflow resume: "Agents that already completed usually return their cached results, and the rest run live." — [Workflows](https://code.claude.com/docs/en/workflows), "Resume after a pause". The prior research established a fork reuses the parent's prompt cache; nothing equivalent is stated for a workflow agent, a teammate, or a background session.

**When the docs say NOT to orchestrate**

- Agent teams, explicitly: "Agent teams add coordination overhead and use significantly more tokens than a single session. They work best when teammates can operate independently. **For sequential tasks, same-file edits, or work with many dependencies, a single session or subagents are more effective.**" — [Agent teams](https://code.claude.com/docs/en/agent-teams), "When to use agent teams"
- Team sizing: "**Diminishing returns**: beyond a certain point, additional teammates don't speed up work proportionally… Three focused teammates often outperform five scattered ones." — [Agent teams](https://code.claude.com/docs/en/agent-teams), "Choose an appropriate team size"
- Task sizing on both sides: "**Too small**: coordination overhead exceeds the benefit. **Too large**: teammates work too long without check-ins, increasing risk of wasted effort. **Just right**: self-contained units that produce a clear deliverable, such as a function, a test file, or a review." — [Agent teams](https://code.claude.com/docs/en/agent-teams), "Size tasks appropriately"
- Cost page, on teams: "For research, review, and new feature work, the extra tokens are usually worthwhile. For routine tasks, a single session is more cost-effective." — [Agent teams](https://code.claude.com/docs/en/agent-teams), "Token usage"
- Workflows, by positive definition rather than prohibition: "A workflow fits best when the task is larger than one agent can hold in context, or when the same step needs to run across many items." And the escalation threshold: "Reach for a workflow when a task needs more agents than one conversation can coordinate". — [Workflows](https://code.claude.com/docs/en/workflows), "Example workflow prompts" and intro
- Ultracode carries its own warning: "This applies to every task in the session, so each request uses more tokens and takes longer than at lower effort levels… Drop back with `/effort high` when you return to routine work." — [Workflows](https://code.claude.com/docs/en/workflows), "Let Claude decide with ultracode"
- Shape evidence for a human-in-the-loop carve-out: `modernize-uplift.md` marks one step "**5a — Pilot (mandatory; do it yourself, in-session, never in a workflow)**" — a pilot must be done by hand before the fan-out is even valid, and `uplift-migrator.md`'s own description says it "Refuses to migrate anything if no playbook exists yet." The workflow's per-unit prompt enforces it: "IF PLAYBOOK.md DOES NOT EXIST, STOP IMMEDIATELY and migrate nothing: this fan-out is only valid after a pilot." — `code-modernization\commands\modernize-uplift.md`, `agents\uplift-migrator.md`, `workflows\uplift-migrate.js`

**Permission and interaction semantics that shape efficiency**

- Workflow agents escape your session's permission mode: "Your permission mode controls only the launch prompt above. **The subagents the workflow spawns always run in `acceptEdits` mode and inherit your tool allowlist, regardless of your session's mode. File edits are auto-approved.** Shell commands, web fetches, and MCP tools that aren't in your allowlist can still prompt you mid-run. To avoid this on a long run, add the commands the agents need to your allowlist before starting." — [Workflows](https://code.claude.com/docs/en/workflows), "Approve the plan before it runs"
- No mid-run human checkpoint exists: "No mid-run user input — Only agent permission prompts can pause a run. **For sign-off between stages, run each stage as its own workflow.**" — [Workflows](https://code.claude.com/docs/en/workflows), "Behavior and limits". This is why the `code-modernization` plugin ships six separate scripts rather than one.
- Teammate permission prompts funnel to the lead and are a documented friction source: "Teammate permission requests bubble up to the lead, which can create friction. Pre-approve common operations in your permission settings before spawning teammates to reduce interruptions." — [Agent teams](https://code.claude.com/docs/en/agent-teams), "Too many permission prompts"
- Cross-agent messages are never consent: "When one agent sends another a message over `SendMessage`, the receiving agent is told it came from another Claude session, not from you. A teammate cannot approve a permission prompt or supply consent on your behalf… the classifier treats an approval claim relayed from another agent as untrusted input rather than confirmation from you." — [Agent teams](https://code.claude.com/docs/en/agent-teams), "Permissions"
- Backgrounded forked skills bypass checkpointing: "A forked skill that runs in the background applies its edits outside your session's checkpoints, so `/rewind` doesn't undo them; use git to revert them." — [Skills](https://code.claude.com/docs/en/skills), "Run skills in a subagent"
- Teams cannot nest and cannot background: "**No nested teams**: teammates cannot spawn their own teammates. Only the lead can manage the team." and "**No background subagents from in-process teammates**… returns an error, because a teammate's background work can't outlive the lead's process." — [Agent teams](https://code.claude.com/docs/en/agent-teams), "Limitations"
- Workflows are unavailable to sub-agents (from the prior research, unchanged): `Workflow` is withheld from every sub-agent, so only the main thread can start one. — [Create custom subagents](https://code.claude.com/docs/en/sub-agents), "Available tools"
- Availability gates: workflows need v2.1.154+, are "available on all paid plans", and on Pro must be turned on in `/config`; they are disabled by `disableWorkflows` or `CLAUDE_CODE_DISABLE_WORKFLOWS=1`. Agent teams are "experimental and disabled by default" behind `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`. Agent view is a "Research preview" needing v2.1.139+. — [Workflows](https://code.claude.com/docs/en/workflows) intro and "Turn workflows off"; [Agent teams](https://code.claude.com/docs/en/agent-teams) Warning; [Agent view](https://code.claude.com/docs/en/agent-view)

- **No experiments were run.** No workflow was executed, no team spawned, no background session dispatched. Every claim is read from documentation or from the literal contents of a shipped file.
- **The plugin scripts are shape evidence, never contract.** `parallel()`, `log()`, `budget.total`/`budget.remaining()`, `meta.whenToUse`, `meta.phases`, the `pipeline()` callback's third argument, the `agent()` options `agentType`/`label`/`phase`/`model`/`effort`, and the `Workflow({scriptPath|name, args})` call shape are all read from `C:\Users\saud-alnasser\.claude\plugins\marketplaces\claude-plugins-official\plugins\`. - **`claude-security/workflows/scan.js` is minified** (31.9 KB on effectively one line). Its API surface was extracted by pattern-counting, not by reading the logic. Its `meta` block was read directly.
- **The agent-view page was fetched as a restructured summary,** not as verbatim source markdown — the fetcher reorganized it under its own headings. ## Open questions

1. **What is the `Workflow` tool's input schema?** The tools reference gives it a one-line table row and no behavior section. `scriptPath`, `name`, and `args` are read from shipped plugin markdown only. Whether `resumeFromRunId` is a real parameter — asserted by `code-modernization/commands/modernize-assess.md` ("note the workflow's `runId` — if the session dies mid-sweep, relaunch with `resumeFromRunId` and completed systems return instantly from cache") — is **unverifiable from the docs**, and it appears to contradict the workflows page's "Resume works within the same Claude Code session. If you exit Claude Code while a workflow is running, the next session starts the workflow fresh." One of these two sources is wrong.
2. **What is the complete workflow script API?** The docs name `agent()`, `pipeline()`, `args`, `meta.name`, `meta.description`, and the `schema` option. Shipped Anthropic scripts additionally use `parallel()`, `log()`, `budget.total`, `budget.remaining()`, `meta.whenToUse`, `meta.phases`, and the options `agentType`, `label`, `phase`, `model`, `effort`. None of these is documented. The documentation is silent.
3. **Is `schema` enforced, and what happens on violation?** The docs show a `schema` option and dereference the result as typed, but never say whether the runtime validates the return, retries a malformed one, or resolves `null`. The documented `null` cases are only "you stop it mid-run or it hits an unrecoverable API error". The documentation is silent.
4. **Can a workflow agent run in a git worktree?** The docs' own example prompt says "transform each one in an isolated copy so edits don't conflict", and shipped scripts say "disjoint directories, so **no worktree isolation is needed**" — both implying the option exists. No option name is documented, and none of the seven official scripts passes one. The documentation is silent on how a workflow requests isolation.
5. **Do hooks fire inside workflow agents?** `SubagentStart`/`SubagentStop` are documented for subagents; a workflow spawns subagents; no page states whether the hooks fire for them, or what `agent_type` a workflow agent reports. Neither the hooks page nor the workflows page addresses it. The documentation is silent — load-bearing if a caller plans to use hooks as a quality gate over a fan-out.
6. **What is the parameter surface for spawning a teammate?** Teammates are spawned by natural-language instruction to the lead throughout the page; the underlying tool call is never shown. `team_name` on the Agent tool is documented as "accepted but ignored". How an agent type, a name, a model, and plan-gating are actually passed is not published.
7. **Is there any documented brief template anywhere?** No. Searched the workflows, agent-teams, agent-view, skills, hooks, agents, tools-reference, and costs pages. The single worked spawn-prompt example on the agent-teams page is the whole corpus. Treating that as a template is inference, not a finding.
8. **Does `TaskCompleted` accept `decision: "block"` or not?** The hooks page's prose says "supports blocking via exit code 2 or `continue: false`" and then shows a `{"decision": "block", "reason": …}` example under that same heading. The page contradicts itself.
